Bora construir o Concord junto

O Concord é de código aberto e feito pela galera. Achou um bug, teve uma ideia ou quer mexer no código? Esta página mostra o caminho inteiro, do relato até a mudança no ar.

  1. Abra uma issueConte o bug ou a ideia no GitHub.
  2. Pegue pra vocêSe atribua e crie uma branch.
  3. Abra um PROs testes rodam sozinhos.
  4. Merge = no arEm ~1 minuto está em produção.

Da ideia até a produção

Toda mudança passa pela mesma esteira. Nada entra na main sem passar pelos testes.

  1. 📝Issueo problema, com print e como repetir
  2. 🌿Branchfix/6-mute-icons
  3. 💾Commitsfix(voice): …
  4. 🔀Pull requestcom Closes #6
  5. 🧪Testestipos, build e dois navegadores numa call
  6. 🚀Mergedeploy automático em concord-community.com
No PR: só os testes, nada vai pro arNa main: testes e, se passar, deploy

A vida de uma issue

Todo trabalho começa numa issue. Assim ninguém faz a mesma coisa duas vezes, e fica registrado o porquê de cada mudança.

aberta→ triagem→ pronta→ em andamento→ PR aberto→ fechada ✓
precisa de info
Falta algo para entender ou repetir. Sem resposta em 14 dias, fecha (dá para reabrir).
duplicada · não vamos fazer
Fecha com um comentário explicando o motivo. Nunca fecha em silêncio.
  1. Aberta: pelo formulário Bug ou Ideia, já entra com a label triagem.
  2. Triagem: um mantenedor confirma que é real, vê se não é duplicada e coloca as labels de tipo, área e prioridade.
  3. Pronta: clara o bastante para alguém pegar. As mais simples ganham good first issue.
  4. Em andamento: antes de começar, se atribua à issue. Se ela já tem dono, combine nos comentários.
  5. PR aberto: a branch e o PR citam a issue (Closes #6).
  6. Fechada: sozinha, quando o PR entra na main. Depois do deploy, confira em produção e avise quem reportou.

Abrindo uma boa issue

  • Procure antes, nas abertas e nas fechadas. Se já existe, comente lá ou deixe um 👍.
  • Uma issue, um assunto. Dois problemas viram duas issues.
  • Título específico: "Ícones de mutado e ensurdecido não aparecem juntos", não "bug no áudio".
  • Como repetir, passo a passo, mais print ou vídeo.
  • Travada, ping alto ou áudio picotando? Anexe uma gravação de diagnóstico: Configurações → Modo desenvolvedor → Gravar, com "Marcar momento" quando acontecer.
🔒 Falha de segurança não vai em issue pública. Use o relato privado do GitHub (detalhes na política de segurança).

Branches

A main é sempre o que está no ar. Cada mudança nasce numa branch própria.

fix/6-mute-icons

Em inglês, minúsculas e hífens. O número da issue é opcional, mas ajuda.

# parte da main atualizada
git switch main && git pull
git switch -c fix/6-mute-icons

# ... commits ...
git push -u origin fix/6-mute-icons
gh pr create

Com os testes passando, faça o merge com "Squash and merge": a branch vira um único commit na main, e o deploy sai sozinho.

Commits

Seguimos o padrão Conventional Commits: dá para entender o histórico só batendo o olho.

fix(voice):show muted and deafened icons together

Título em inglês, minúsculo, sem ponto final, até ~72 caracteres. No corpo, explique o porquê: o problema, a causa e o que mudou.

featfuncionalidade nova
fixcorreção de bug
perfmais rápido ou mais leve
refactorreorganiza sem mudar o comportamento
docsdocumentação
testtestes
builddependências, Docker, Electron
ciGitHub Actions
stylesó formatação
choremanutenção em geral

Escopos do projeto (opcionais): client, server, desktop, voice, chat, auth, deploy, db. Quebrou compatibilidade? Use ! (ex.: feat(auth)!:) e explique no rodapé BREAKING CHANGE:.

✅ Para a issue fechar sozinha, escreva Closes #6 no corpo do commit ou na descrição do PR. Só "(issue #6)" cria o link, mas não fecha.

Commits assinados (obrigatório)

O repositório recusa push de commits sem assinatura verificada. A assinatura prova que o commit é seu, e não de alguém que só usou o seu nome no Git. No GitHub, eles aparecem com o selo Verified.

  1. 🔑Crie uma chavessh-keygen -t ed25519 -f ~/.ssh/github_signing
  2. ⚙️Configure o Gitpara assinar todo commit com ela
  3. ☁️Cadastre no GitHubcomo Signing Key, não Authentication
  4. ✔️Verifiedtodo commit seu passa a ser aceito
# uma vez por computador
ssh-keygen -t ed25519 -C "seu@email.com" -f ~/.ssh/github_signing
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/github_signing.pub
git config --global commit.gpgsign true

# cadastra a chave no GitHub como chave de assinatura
gh auth refresh -h github.com -s admin:ssh_signing_key
gh ssh-key add ~/.ssh/github_signing.pub --type signing

O e-mail dos seus commits precisa ser um e-mail verificado na sua conta do GitHub. Os merges pelo botão do PR o GitHub assina sozinho.

Rodando na sua máquina

Precisa de Node 24 e Docker Desktop.

# voz e vídeo (LiveKit)
docker compose -f docker-compose.dev.yml up -d livekit

# servidor — recarrega sozinho
cd server && npm install && npm run dev

# cliente (outro terminal) — abra http://localhost:5173
cd client && npm install && npm run dev

Antes de abrir o PR, rode npx tsc --noEmit no server e npm run build no client, e teste o fluxo na mão (com duas contas, se envolve outra pessoa).
